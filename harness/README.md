# Измерительная обвязка к эксперименту Э3

Обвязка к разделу 3.5 диссертации. Позволяет получить **собственные** измерения
времени обнаружения отказа и частоты ложных срабатываний на стенде раздела 2.1.

> Числа в таблицах 3.5–3.8 сейчас порождены `synth.py` (статистическое
> моделирование). Их заменяют протоколы, полученные этой обвязкой.

## Стенд (раздел 2.1, таблица 2.1)

Пять арендованных физических серверов x86 с выделенными ядрами у одного поставщика,
частная сеть в пределах площадки, транспортная сеть поставщика между площадками.

| Узел | Площадка | Роль | Кворум |
|---|---|---|---|
| С1 | Москва | управление, хранение состояния инфраструктуры; резервный экземпляр функции | да |
| С2 | Москва | узел обработки, объект внесения отказа | нет |
| И | Москва | источник нагрузки и измеритель, вне инфраструктуры | нет |
| С3 | Санкт-Петербург | управление, хранение состояния инфраструктуры | да |
| С4 | Санкт-Петербург | управление, хранение состояния инфраструктуры | да |

Путь трафика (И → направляющий узел → экземпляры на С2 и С1) целиком лежит на
площадке «Москва»: иначе *T*р измерялось бы транспортной сетью, а не механизмом
(требование Т5). Межплощадочный канал нужен для части 4 Э3 — раздельного измерения
вероятности непринятия p — и для главы 5 (кворум 1 + 2).

Детектор запускается на узле, направляющем трафик (наблюдатель), и на узлах,
несущих экземпляры. Для проверки связности и отладки достаточно двух узлов — С1 и С2.

## Состав

| Файл | Назначение |
|---|---|
| `detector.go` | детектор отказа: двусторонний обмен контрольными сообщениями, правила переходов раздела 3.4 |
| `run_experiment.sh` | серия повторностей с внесением отказа и записью моментов |
| `analyze.py` | обработка протоколов: среднее, медиана, доверительный интервал, проверка критерия К2 |
| `synth.py` | **модельные** данные для таблиц 3.5–3.8 и рисунков 3.6, 3.7 (не измерения) |
| `e1_example.py` | **модельный** пример обработки Э1 для таблицы 2.8 (не измерения) |

## Сборка

```
go build -o detector detector.go
```

Все серверы стенда x86-64, кросс-сборка не нужна. Двоичный файл копируется на каждый узел.

## Проверка связи

На С2:

```
./detector -listen :4000 -peer <адрес-С1>:4000 -tau 26ms -k 5 -m 3 -log /tmp/c2.jsonl
```

На С1:

```
./detector -listen :4000 -peer <адрес-С2>:4000 -tau 26ms -k 5 -m 3 -log /tmp/c1.jsonl
```

В течение секунды оба узла должны напечатать «ВОЗВРАТ: путь работоспособен».
После снятия питания С2 узел С1 печатает «ОТКАЗ» в пределах от (k − 1)τ = 104 мс
до kτ = 130 мс.

## Прогон серии

На наблюдателе:

```
MODE=process PEER=<адрес-С2> REPS=30 ./run_experiment.sh
```

Режимы внесения отказа (соответствие видам отказа раздела 2.3):

- `power` — снятие электропитания С2 через контроллер управления сервера, операция
  ForceOff (О1). Заполнить `POWER_OFF_CMD` и `POWER_ON_CMD`, например запросом
  `POST /redfish/v1/Systems/<id>/Actions/ComputerSystem.Reset` с телом
  `{"ResetType":"ForceOff"}` / `{"ResetType":"On"}` к контроллеру управления С2.
  Учётные данные контроллера передавать через переменные окружения, не в скрипте.
- `link` — разрыв связности через nftables на стороне наблюдателя (О2).
- `pause` — приостановка процесса на встречном узле сигналом SIGSTOP (О3):
  воспроизводит зависание, сигнал не перехватывается.
- `process` — завершение процесса на встречном узле (`kill -9`). Даёт иной путь
  наблюдения, чем О3; применяется для отладки и сопоставления.

Результаты складываются в каталог `run-<дата>`: протокол детектора, моменты
внесения отказов, отчёт. Каталог целиком идёт в приложение диссертации как
протокол измерений.

## Три вещи, которые надо учесть в методике

**Фаза внесения отказа.** Время обнаружения зависит от того, в какой момент
цикла контрольных сообщений произошёл отказ: оно лежит в пределах от (k−1)τ до
kτ. Если отказ вносить всегда в одной и той же точке цикла, измеренное среднее
систематически сместится к границе вместо расчётного (k−1/2)τ. При проверке
обвязки на пяти повторностях без рандомизации получено среднее 130 мс при
расчётных 117 мс именно по этой причине. `run_experiment.sh` поэтому перед каждым
внесением выдерживает случайную паузу, равномерную на [0, τ).

**Синхронизация часов.** В режимах `process` и `pause` момент отказа фиксируется на
одном узле, а обнаружение — на другом. При измеряемых величинах порядка сотни
миллисекунд рассогласование часов в десятки миллисекунд искажает результат.
Настроить синхронизацию до первого измерения и измерить остаточное
рассогласование отдельно (раздел 2.4). В режимах `link` и `power` момент отказа
фиксируется на том же узле, что и обнаружение, и вопрос не возникает.

**Число повторностей.** Раздел 3.5 требует не менее 30 на сценарий, уточнение — по
формуле (2.6). `analyze.py` предупреждает, если их меньше, и рассчитывает
доверительный интервал по распределению Стьюдента. Порядок обработки при
отсутствии нормальности (медиана, порядковые статистики) — по разделу 2.4.

## Ложные срабатывания (часть 2 эксперимента Э3)

Внести потери в канал контроля и наблюдать длительно:

```
sudo tc qdisc add dev <интерфейс> root netem loss 10%
./detector -listen :4000 -peer <адрес-С2>:4000 -tau 26ms -k 5 -m 3 -log fp.jsonl
```

Число событий `down` при работоспособном встречном узле — это ложные признания
отказа. Расчёт по (3.18) при p = 0,01 и k = 5 даёт около 0,12 события в год,
поэтому потери задаются заведомо большими — диапазон 0,10–0,30 с шагом 0,05
(раздел 2.3, таблица 2.4), — а результат пересчитывается на эксплуатационное
значение p. Отдельным сценарием — пачечные потери (`netem loss gemodel …`),
при той же средней вероятности.

## Естественная вероятность непринятия (часть 4 эксперимента Э3)

Без внесения потерь, раздельно для внутриплощадочного канала (С1 ↔ С2) и
межплощадочного (С1 ↔ С3). Непринятым считается сообщение, потерянное либо
принятое позже периода τ.
