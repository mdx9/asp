# Измерительная обвязка к эксперименту Э3

Обвязка к разделу 3.5 диссертации. Позволяет получить **собственные** измерения
времени обнаружения отказа и частоты ложных срабатываний на двух физических
узлах — персональном компьютере и одноплатном компьютере Raspberry Pi.

Двухузловая конфигурация достаточна: в опубликованных исследованиях
отказоустойчивости в контейнерной инфраструктуре применялся стенд того же
масштаба. Четыре узла нужны только для эксперимента Э5 главы 5 (кворум).

## Состав

| Файл | Назначение |
|---|---|
| `detector.go` | Детектор отказа: двусторонний обмен контрольными сообщениями, правила переходов по разделу 3.4 |
| `run_experiment.sh` | Прогон серии повторностей с внесением отказа и записью моментов |
| `analyze.py` | Обработка протоколов: среднее, медиана, доверительный интервал, проверка критерия К2 |

## Сборка

```
go build -o detector detector.go                          # для ПК
GOOS=linux GOARCH=arm64 go build -o detector-arm64 detector.go   # для Raspberry Pi
```

Скопировать `detector-arm64` на Pi, переименовать в `detector`, дать право на запуск.

## Проверка связи

На Pi:

```
./detector -listen :4000 -peer <адрес-ПК>:4000 -tau 26ms -k 5 -m 3 -log /tmp/pi.jsonl
```

На ПК:

```
./detector -listen :4000 -peer <адрес-Pi>:4000 -tau 26ms -k 5 -m 3 -log /tmp/pc.jsonl
```

В течение секунды оба узла должны напечатать «ВОЗВРАТ: путь работоспособен».
Выдернуть питание Pi — ПК печатает «ОТКАЗ» примерно через 130 мс.

## Прогон серии

```
MODE=process PEER=192.168.1.20 REPS=30 ./run_experiment.sh
```

Режимы внесения отказа:

- `process` — остановка процесса на встречном узле по SSH. Момент отказа известен точно.
- `link` — разрыв связности через nftables на стороне наблюдателя.
- `power` — обесточивание управляемой розеткой; заполнить `POWER_OFF_CMD` и `POWER_ON_CMD`.

Результаты складываются в каталог `run-<дата>`: протокол детектора, моменты
внесения отказов, отчёт. Каталог целиком идёт в приложение диссертации как
протокол измерений.

## Три вещи, которые надо учесть в методике

**Фаза внесения отказа.** Время обнаружения зависит от того, в какой момент
цикла контрольных сообщений произошёл отказ: оно лежит в пределах от (k−1)τ до
kτ. Если отказ вносить всегда сразу после приёма очередного сообщения,
измеренное среднее систематически сместится к верхней границе kτ вместо
расчётного (k−1/2)τ. При проверке обвязки на пяти повторностях получено среднее
130 мс при расчётных 117 мс именно по этой причине. Момент внесения отказа
необходимо рандомизировать в пределах периода τ — иначе измеряется не то, что
рассчитано. Это существенное замечание для раздела 2.3.

**Синхронизация часов.** В режиме `process` момент отказа фиксируется на одном
узле, а обнаружение — на другом. При измеряемых величинах порядка сотни
миллисекунд рассогласование часов в десятки миллисекунд искажает результат.
Настроить синхронизацию до первого измерения и измерить остаточное
рассогласование отдельно. В режимах `link` и `power` момент отказа фиксируется
на том же узле, что и обнаружение, и вопрос не возникает.

**Число повторностей.** Раздел 3.5 требует не менее 30 на сценарий.
`analyze.py` предупреждает, если их меньше, и рассчитывает доверительный
интервал по распределению Стьюдента.

## Ложные срабатывания (часть 2 эксперимента Э3)

Внести потери в канал контроля и наблюдать длительно:

```
sudo tc qdisc add dev eth0 root netem loss 1%
./detector -listen :4000 -peer <адрес-Pi>:4000 -tau 26ms -k 5 -m 3 -log fp.jsonl
```

Число событий `down` при работоспособном встречном узле — это ложные признания
отказа. Расчёт по (3.18) при p = 0,01 и k = 5 даёт около 0,12 события в год,
поэтому для получения содержательной оценки потери задаются заведомо большими
(5–20 %), а результат пересчитывается на эксплуатационное значение p.
